## Executive Summary

This is the v3 audit. v2 closed 12 of 38 v1 findings and addressed 9 of its
own new findings. v3 focused on the **delta from v2**: re-verifying that
v2 fixes did not regress, and re-scanning for issues that the v1/v2 audits
either missed or could not have seen.

**No v2 regressions detected.** All 16 v2 fixes still pass direct
file/pattern verification (see Verification Matrix below).

**4 new v3 findings**, all of which I introduced or surfaced as a result
of v2 code paths:
- 2 HIGH in code I wrote in v2 (unbounded `rateBuckets` map, unbounded
  `api_dump/` disk consumption) — these are the most consequential v3
  findings because they represent DoS vectors I myself introduced.
- 1 MEDIUM in code the v1/v2 audits did not touch (`apiextract` HTTP
  client without timeout).
- 1 LOW in a v1 backlog item (`benchCmd` placeholder that survived both
  v1 and v2 audits).

All 4 v3 findings are REMEDIATED in this audit. The repo now passes
gofmt, go vet, and 203/203 unit tests (up from 198 in v2).

The v3 cycle also caught a class of issue worth highlighting for future
audits: **code introduced by prior audit remediation can itself contain
new bugs**. v2 added a per-client rate-limit map; that map had no eviction
strategy. v2 added an `api_dump/<timestamp>` directory per `/crawl`; that
directory had no quota. Both were invisible to v2's static review because
they required considering adversarial input over time. v3's perspective —
"how does an attacker use this against the system?" — caught them.

## v3 NEW Findings (Full Detail)

### [V3-1] Unbounded `rateBuckets` map — memory exhaustion DoS
- **Severity:** HIGH
- **Dimension:** D7 — Performance / D8 — Resource Abuse
- **File:** `internal/api/api.go:30` (v2-introduced)
- **Introduced in:** v2 (this finding was created by the v2 audit itself)
- **Finding:** The v2 rate limiter stores one `clientBucket` per unique
  client IP in a Go map. There is no eviction. An attacker (or a misbehaving
  load balancer) can send one request per spoofable source IP and grow the
  map without bound. Each `clientBucket` is ~40 bytes; 1M unique IPs = ~40 MB.
  An attacker who can spray source IPs at the rate limiter (or via X-Forwarded-For
  if behind a proxy without rate limiting) can OOM the process.
- **Evidence:**
  ```go
  type Server struct {
      ...
      rateBuckets map[string]*clientBucket  // no eviction
  }
  func (s *Server) allowRequest(remoteAddr string) bool {
      ...
      s.rateBuckets[clientKey] = &clientBucket{...}  // grows forever
  }
  ```
- **Impact:** Memory exhaustion DoS via legitimate `/crawl` endpoint.
  Attacker needs network access to the API port but does NOT need auth
  (rate limit middleware is applied AFTER auth, so unauthenticated probe
  traffic is still rate-limited — and still creates buckets).
- **Remediation:**
  - Added `bucketTTL` (default 10 min), `maxBuckets` (default 10,000),
    `lastSweepAt`, `sweepEvery` (default 60s) to Server.
  - `sweepStaleBuckets(now)` runs every `sweepEvery` to evict buckets
    older than `bucketTTL`.
  - `evictOldestLocked(now)` runs when `len(rateBuckets) >= maxBuckets`
    to cap absolute memory usage.
  - All knobs are configurable via `AEGIS_API_BUCKET_TTL_SEC`,
    `AEGIS_API_MAX_BUCKETS`, `AEGIS_API_SWEEP_EVERY_SEC`.
- **Tests added (3):**
  - `TestRateLimitBucketEvictionAtMaxBuckets` — 5 distinct clients with
    `maxBuckets=3` results in exactly 3 entries (oldest LRU-evicted).
  - `TestRateLimitBucketSweepRemovesStale` — buckets with `lastRefill`
    older than TTL are deleted; fresh ones remain.
  - `TestRateLimitSweepRunsPeriodically` — sweep fires when
    `now.Sub(lastSweepAt) > sweepEvery` (covers the lazy-trigger path).
- **Effort:** M

### [V3-2] Unbounded `api_dump/` directory creation — disk exhaustion DoS
- **Severity:** HIGH
- **Dimension:** D7 — Performance / D8 — Resource Abuse
- **File:** `internal/api/api.go:97-110` (v2 code path)
- **Finding:** Every authenticated `/crawl` request creates a new
  timestamped subdirectory under `api_dump/`. There is no upper bound on
  the number of subdirectories. The crawler then writes screenshots,
  downloaded content, and HTML into that directory. An attacker with a
  valid token (or in `AEGIS_API_ALLOW_UNAUTH=true` mode) can submit one
  `/crawl` request per second and fill the disk.
- **Evidence (v2 code):**
  ```go
  go func() {
      dumpPath := filepath.Join("api_dump", time.Now().UTC().Format("20060102_150405.000000000"))
      ...
  }()
  ```
- **Impact:** Disk exhaustion DoS. 60 requests/minute × (crawl output
  size) = O(gigabytes/day).
- **Remediation:**
  - Extracted directory creation to `prepareCrawlDumpDir()`.
  - `prepareCrawlDumpDir` reads existing entries under the root, sorts
    by name (lexical = chronological for our format), and deletes the
    oldest N until `len < maxDumpDirs - 1` before creating the new
    directory.
  - New env vars: `AEGIS_API_DUMP_MAX_DIRS` (default 16),
    `AEGIS_API_DUMP_ROOT` (defaults to `api_dump`).
  - Errors during sweep are logged but do not block crawl start.
- **Tests added (2):**
  - `TestPrepareCrawlDumpDirPrunesOldest` — 5 pre-existing dirs,
    `max=3` → 3 dirs after call; 2 oldest are gone.
  - `TestPrepareCrawlDumpDirRespectsRootOverride` — env var
    `AEGIS_API_DUMP_ROOT` redirects the location.
- **Effort:** M

### [V3-3] `apiextract.NewExtractor` builds `http.Client` with no Timeout
- **Severity:** MEDIUM
- **Dimension:** D7 — Performance / D9 — Error Handling
- **File:** `internal/apiextract/extractor.go:40-50`
- **Finding:** `NewExtractor` builds `&http.Client{}` with no Timeout
  and no per-request context. A slow or unresponsive target can hang
  the goroutine forever. This is the same anti-pattern as v1 H-007
  (missing browser operation timeouts) but for the API extractor.
- **Evidence:**
  ```go
  e := &Extractor{
      allowPrivateHosts: true,
      httpClient:        &http.Client{},  // no Timeout, no Transport
  }
  ```
- **Impact:** Resource leak / DoS surface: an extractor call against a
  hanging target consumes a goroutine indefinitely. Combined with
  concurrent scan orchestration (`internal/integration/complete.go`),
  this can exhaust the goroutine pool.
- **Remediation:**
  - Added `timeout time.Duration` field to `Extractor` (default 30s).
  - Added `WithTimeout(d time.Duration)` functional option.
  - `NewExtractor` now initializes the http.Client with the timeout.
- **Effort:** S

### [V3-4] `benchCmd` placeholder (v1 L-001 not fixed in v1 or v2)
- **Severity:** LOW
- **Dimension:** D1 — Code Quality / D14 — Testing
- **File:** `cmd/aegis/main.go:209-226`
- **Finding:** `benchCmd` was marked as a v1 LOW finding (L-001) and was
  not fixed in v2. The placeholder body prints fake timing data and
  returns nil, which is misleading — it suggests a benchmark ran when
  none did.
- **Evidence (pre-v3):**
  ```go
  RunE: func(cmd *cobra.Command, args []string) error {
      start := time.Now()
      // Simple benchmark logic
      fmt.Printf("Benchmarking target: %s\n", target)
      // Implementation...
      duration := time.Since(start)
      fmt.Printf("Completed in %v\n", duration)
      return nil
  },
  ```
- **Impact:** Operator confusion. A user running `aegis bench --target ...`
  sees a fake "Completed in 0s" message and may believe the benchmark ran.
- **Remediation:**
  - Replaced the body with an explicit error pointing to `go test -bench`.
  - Updated `--target` flag help to "Ignored — kept for v0.0.1 CLI compatibility".
  - Updated `Short` to "Placeholder — use `go test -bench` for actual benchmarks".
  - Removed unused `time` import.
- **Effort:** S
